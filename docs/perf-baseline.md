# Performance baseline and results

Fixture: `tests/fixtures/kitchen.aaw`, generated by `tests/fixtures/kitchenGenerator.ts` from the app's own cabinet code.
16 cabinets (6 base, 5 wall, 2 tall, 3 island), 347 parts, 667 joints, 488,567 bytes, no validation warnings.

## Method

- Model timings: `AA_PERF_OUT=/tmp/x.json npx vitest run tests/perf/measure.test.ts` (see `tests/perf/harness.ts`).
  Three runs per side, median reported, before and after measured in the same session on a machine shared with
  other agents. "Cold" means caches empty, "warm" means a repeat call.
- App timings: Playwright against the built Electron app (`tests/e2e/perf-large.spec.ts`). The sandbox renders with
  software GL, so frame times there are not meaningful; only JS time and draw counts are.
- Profiles: node `--cpu-prof` for the model, CDP Profiler for the app.
- Outputs are guarded by `tests/perf/kitchenOutputs.test.ts`, which compares against
  `tests/fixtures/kitchen.expected.json` (cut list, CSV, shopping list, sheet layouts, warnings, interferences,
  clearances, and SHA-1 hashes of every build plan page). It was recorded from the code before any change.
  Re-record only on purpose with `AA_WRITE_FIXTURE=1`.

In the app (e2e, software GL): open to first frames 382 ms, 695 draw calls and 61,726 triangles per frame; a
dimension edit reaches JS idle in about 133 ms; the cut list opens in about 1 s with 98 rows.

## What changed and why

- `worldBox` and `rotateVec` work out sines and cosines once per board (bit-identical arithmetic).
- `validate` swept every pair of parts and recomputed boxes each time. It now computes each box once, sweeps on x,
  and looks up contacts, grooves and groups through maps. This was the largest single cost.
- Group, joint-formula, follow-motion and hardware-pruning lookups use WeakMap indexes keyed by array identity
  instead of linear scans; the cut list reads each part's joints from the same index.
- Finished part shapes (the CSG result) are cached in a bounded LRU, and interference pair volumes are cached by
  shape and placement, so repeated checks and edits to unrelated parts do not redo CSG. The Build Plan benefits
  from the shape cache.
- Tests: equivalence tests (`tests/model/perfEquivalence.test.ts`) compare each fast path with a reference
  implementation; `tests/perf/largeProject.test.ts` holds generous, machine-scaled budgets.

## Remaining costs and follow-ups

- Cold CSG (about 1 s for joinery, interferences and clearance on first use). A worker or progress indicator
  would hide it.
- Create Build Plan is about 8.5 s, almost all hidden-line ray casting in `src/drawings/lines.ts` (about 700k
  rays). A micro-optimisation there gained about 5% and was reverted. Real gains need a worker, progress UI, or a
  coarser sampling strategy. The build-plan area belongs to another agent, so it was left alone.
- Selecting a part costs about 65 ms of JS in the app, spent re-rendering 347 `BoardMesh` components.
  Memoising `BoardMesh` was tried and measured no gain (65 ms with and without), so it was reverted.
